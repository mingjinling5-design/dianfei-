当前版本使用 Django 网站会话、按用户隔离的数据表及加密的易校园授权信息。每个人使用自己的手机号完成验证码登录，查看各自宿舍与历史数据。

# ⚡ yischool-power · 寝室电费监测与用电分析

针对 **易校园 / 一卡通寝室电费** 的自建采集 + 分析 + 可视化系统。

### 分摊预估

宿舍几个人分摊电费，直接在余额下面算好：

```
分摊预估                        [4 人][5 人]
每人每月 76 元
4 人合计 306 元/月 · 按有人住的 24 天算 · 跳过 6 天没住人 · 下次充 153 元时每人 38 元
```

- **数据来源**：用拟合出来的日耗（加权回归 + EWMA，见 §8.4）乘 30 天得到月合计，再按人数摊
- **按有人住的天数算**：放假/实习那几天宿舍没人，消耗掉到底噪，这些天不计入日均
- **实时**：每轮采集后重新计算，不是写死的
- **默认 4 人**，可切到 5 人，选择记在浏览器里（下次打开还是你选的）
- 默认人数也能在 `config.yaml` 里改：

```yaml
app:
  people: 4                 # 默认人数
  people_options: [4, 5]    # 可切换的选项
```

### 预测区间与充值时机

余额趋势图上，预测线外面有一层浅色带 —— 那是**乐观/悲观区间**：

```
大约 2026-10-11 用完，快的话 10月10日，慢的话 10月13日
```

充值时机也是算出来的 —— **在余额跌到提醒线之前 2 天**提示：

```
💡 建议 10月7日前充 153 元，够用一个月
```

跑到提醒线才充就有点赶了，所以往前留了 2 天缓冲。

### 空置期识别

放假回家、长期实习这类**连续多天几乎不住人**的时段会被自动识别并跳过，不计入日均。

判据是**相对的**：拿每天和「本寝室近期中位数」比，低到 25% 以下才算低。

**重点是和「异常值」区分开** —— 上学期间宿舍一般都有人，偶尔一天特别低更可能是数据问题
而不是没人。所以判定要求四条同时成立：

| 条件 | 门槛 | 挡住什么 |
|---|---|---|
| 连续天数够长 | ≥ 4 天 | 单天偏低 → 判为异常，不是空置 |
| 掉到底噪 | < 本寝室中位数的 25% | 只是"略低"（比如省着用）不算 |
| 段内稳定 | 最高/最低 ≤ 3 倍 | 忽高忽低是数据抖动，不是没人 |
| 不撞上停更 | 不与「余额不变」区间重叠 | 上游没更新 ≠ 没人住 |

实测四种情况：

```
真放假（连续 6 天掉到底噪）      -> 识别为空置 ✓
单天异常（只低 1 天）            -> 不识别 ✓
连续 3 天低（未达 4 天门槛）      -> 不识别 ✓
忽高忽低（像数据抖动）            -> 不识别 ✓
```

**手动指定最可靠** —— 你自己清楚什么时候不在：

```yaml
vacancy:
  auto: true            # 关掉就只用手动指定的时段
  ratio: 0.25
  min_days: 4
  periods:
    - { from: "2026-07-01", to: "2026-08-31", note: "暑假" }
```

识别到时页面会提示：

```
🏠 10月1日 ~ 10月6日 有 6 天几乎没用电（每天 0.5 元，平时约 10.0 元）。
   这几天没有计入日均，免得把预测推偏。
```

不这么做的话，放假回来会发现预测说"还能用 30 天"，实际快断电了。

### 自定义时间范围

顶部有快捷区间（近 7 天 / 30 天 / 90 天 / 近一年）和**两个日期框**，可以选任意区间：

```
[近 7 天][近 30 天][近 90 天][近一年]        2026-08-01 ~ 2026-09-26
```

日期框是唯一事实来源 —— 点快捷按钮会把日期填进去，两边永远一致。

### 功率换算

余额差 ÷ 电价 = 度数，度数 ÷ 时长 × 1000 = 平均功率（瓦）。所以**每个小时的功率能算出来**：

```
09-25 各小时功率
  03:00    427 W  ███
  07:00    242 W  ██
  13:00    985 W  ████████     ← 空调开始工作
  17:00   1673 W  █████████████
  20:00   2528 W  █████████████████████   ← 峰值，像是在用烧水壶

  平均功率 886 W · 最高 2528 W · 夜间基础 335 W
  档位分布：大功率 6h · 高功率 3h · 较高 7h · 中等 6h
```

功率档位对照（宿舍常见电器，仅供参考）：

| 档位 | 功率 | 大概是什么 |
|---|---|---|
| 待机档 | < 50 W | 路由器、台灯、充电器 |
| 小功率 | 50–150 W | 笔记本电脑、电风扇 |
| 中等 | 150–350 W | 台式电脑、小冰箱 |
| 较高 | 350–700 W | 洗衣机、投影仪 |
| 高功率 | 700–1500 W | 空调 |
| 大功率 | > 1500 W | 烧水壶、电暖器、电吹风 |

> **两个必须说清楚的前提：**
> 1. 这是**整个房间**的功率，不是某一台设备的。1 小时的粒度分不出是哪台设备在用。
> 2. 是**这一小时的平均功率**，不是瞬时功率。空调只开了 30 分钟，这一小时的平均值就是它满功率时的一半。
>
> 好处是它能揪出「一直开着的电器」—— 实测这个寝室凌晨 2~6 点仍有 335 W，
> 折算下来**一个月约 130 元**，这部分钱不查永远不知道。

界面上还有个**电器耗电估算器**：选个功率（或点预设：空调 1000W / 台式电脑 300W / 烧水壶 1800W…）
加每天开多久，直接算出一个月多少钱。

在终端里也有：

```
  功率换算（2026-09-25）
    平均功率      886 W
    最高功率      2528 W  (20 点左右 · 烧水壶或电暖器)
    夜间基础      335 W  → 一个月约 130 元（可能有电器常开）
    档位分布      大功率6h  高功率3h  较高7h  中等6h
```

### 对比与建议

界面上还有两块：**分析建议**（自动给出的人话结论）和 **花费对比**（环比/同比）。

```
分析建议
  🔌 有电器连续开了很久
     2026-09-25 13:00 起连续 9 小时没停，这段花了 7.60 元。
  📈 最近4天比之前多花了 25%
     前 4 天平均每天 11.14 元，最近 4 天涨到 13.92 元。
  🗓 每月大约花 309 元
  💰 建议充 156 元
  ⚡ 19点、20点、23点 花得最多

花费对比
  今天      截至 11:00   2.55 → 2.61 元   → +2%
  最近一周  7 天 vs 前 7 天  78.00 → 97.00 元  ↑ +24%
  最近一月  还需要大约 1 天数据才能对比
  去年同期  需要满一年数据才能对比
```

**对比的公平性**：两边窗口长度必须一样。

- 「今天 vs 昨天」按**同一时刻**截断（今天只到 11 点，昨天也只算到 11 点），不拿半天比整天
- 「最近一周」在数据不足时**自动缩短窗口**（比如只有 5 个可用日就 2 天 vs 2 天），
  并在界面上写明实际比的是几天
- 数据真的不够时**不硬凑**，直接告诉你还差几天

**建议是规则算出来的，不用大模型**：环比涨跌、月度预估、充值金额与时机、
高峰时段、工作日 vs 周末、长时间没关的电器、异常偏高的日子、数据停更提醒。

界面文案只讲人话，**不出现**「上游 / 数据源 / 读数 / 覆盖率 / σ / MAD / P90 / 接口 / 统计口径 / 环比」这类词。
技术细节全部收进页脚折叠的「关于这些数据」，且只在真有问题时才主动提示
（比如易校园停更、登录过期）。

截图：`docs/mobile.png`（手机 390px）、`docs/desktop.png`（电脑 1280px）、`docs/login.png`。

## 二、这个网页到底是怎么做的（逆向结论）

`https://tool.no-fish.cn/yischool/home` 是一个 **Vue 3 SPA + 自建后端代理**，本身不产生数据，只是把易校园的接口包装了一层。

### 2.1 前端结构

```
/yischool/home                          → 893 字节的 SPA 壳（<div id="app">）
/assets/index-*.js                      → 路由 + 懒加载
/assets/HomeView-*.js                   → 主页面（1.1 MB，内含 ECharts）
/assets/userStore-*.js                  → 全部 API 调用集中在这里
/assets/LocationView-*.js               → 宿舍位置逐级选择
/assets/useApi-*.js, useNotification-*  → Vue / Antd / Pinia / ECharts 运行时
```

真正的接口定义全在 `userStore-*.js` 里，未压缩前长这样：

```js
const s = `/api/yischool`
c = (phone) => POST(`${s}/user/login/send-code`, { phone })
l = (phone, code, school_code, school_name) => POST(`${s}/user/login`, {...})
p = (phone) => GET(`${s}/user/${phone}`)
m = (phone, settings) => PUT(`${s}/user/${phone}/settings`, settings)
h = (phone, location) => POST(`${s}/user/${phone}/location`, location)
_ = (phone, school_code) => GET(`${s}/electric/areas`, { phone, school_code })
v = (phone, area_id) => GET(`${s}/electric/buildings`, { phone, area_id })
y = (phone, area_id, building_code) => GET(`${s}/electric/floors`, {...})
b = (phone, area_id, building_code, floor_code) => GET(`${s}/electric/rooms`, {...})
x = (school_name) => GET(`${s}/electric/schools`, { school_name })
S = (phone) => GET(`${s}/electric/surplus`, { phone })
C = (phone, days = 7) => GET(`${s}/electric/records/${phone}`, { days })
```

### 2.2 完整接口清单（已实测可用）

| 方法 | 路径 | 说明 | 实测 |
|---|---|---|---|
| POST | `/api/yischool/user/login/send-code` | 发短信验证码 | — |
| POST | `/api/yischool/user/login` | 手机号+验证码登录 | — |
| POST | `/api/yischool/user/{phone}/relogin/send-code` | 重新登录发码 | — |
| POST | `/api/yischool/user/{phone}/relogin` | 重新登录 | — |
| GET | `/api/yischool/user/{phone}` | 用户信息（含绑定宿舍、`need_relogin`、`need_location`） | `404 用户不存在` ✅ 通 |
| PUT | `/api/yischool/user/{phone}/settings` | 改配置 | — |
| POST | `/api/yischool/user/{phone}/location` | 绑定宿舍位置 | — |
| GET | `/api/yischool/electric/schools?school_name=` | **学校列表（公开，无需登录）** | `200` 返回 18 所学校 ✅ |
| GET | `/api/yischool/electric/areas` | 校区 | — |
| GET | `/api/yischool/electric/buildings` | 楼栋 | — |
| GET | `/api/yischool/electric/floors` | 楼层 | — |
| GET | `/api/yischool/electric/rooms` | 房间 | — |
| GET | `/api/yischool/electric/surplus?phone=` | **当前余额** | `404 用户不存在` ✅ 通 |
| GET | `/api/yischool/electric/records/{phone}?days=N` | **历史记录** | — |

**关键点**：它的"历史"接口 `records/{phone}` 默认只给 **7 天**，而且返回的是稀疏点。
这就是"统计太草率"的根源——**数据源头就只有 7 天，前端再怎么画也只能画 7 天**。

### 2.3 它的上游

再往下追一层，no-fish 的后端代理的是易校园（小富宝 / 正元智慧）的开放接口：

```
https://application.xiaofubao.com/app/electric/queryISIMSRoomSurplus
   Cookie: shiroJID=<uuid>
   body:   ymId / areaNo / buildNo / floorNo / roomNo
```

`shiroJID` 是登录态，抓包即可拿到（见 [第六节](#六接入真实数据)）。

### 2.4 它的数据链路

```
易校园 App 服务端
   └─ shiroJID + ymId
        └─ tool.no-fish.cn 后端代理（FastAPI 风格，/api/yischool/*）
             └─ Vue SPA（内存里存 7 天，刷新即丢）
                  └─ ECharts 画两条线
```

**没有任何持久化**。关掉页面，历史就没了。

## 六、接入真实数据

编辑 `config.yaml` 的 `source` 段。三种模式：

### ⚠️ 关于单位（很重要）

上游 `surplus` / `records` 接口返回的字段是 **`surplus_amount`，单位是「元」（剩余金额），不是度**。
实测确认（no-fish 前端渲染为 `<span>152.74</span><span>元</span>`，告警线也是按元设的）：

```json
{"phone":"138****0000", "surplus_amount":152.74,
 "queried_at":"2026-09-26T02:37:42Z", "room_name":"西生活区 3号楼 502"}
```

所以本项目：

- **元是权威值**，存储、计算、预测全部在元上做（不做有损折反推）
- **度是按电价折算的派生值**，电价为 `rooms[].unit_price`（默认 0.538 元/度）
- 仪表盘右上角有 **元 / 度 单位切换**，两者同时给出

```
当前余额   152.74 元  (283.9 度)      152.74 / 0.538 = 283.9
近 7 日累计 35.22 元  (65.47 度)
消耗速率   6.16 元/天 (11.45 度/天)
```

> 注意：`queried_at` 是 **UTC**，本项目入库时会转成本地时间。

### 模式 A：`nofish`（推荐 —— 单一学校 + 验证码登录 + 不抓包）

```yaml
source:
  type: nofish
  base_url: https://tool.no-fish.cn
  phone: ""            # 登录后自动写入，不用手填
  school_code: ""      # 登录时选一次，之后固定
  school_name: ""
```

**你只需要做一件事：打开 `http://127.0.0.1:8787/login`，输手机号和验证码。**

原理：登录由本项目自己的后端完成（`ysp/auth.py`），它替你调用易校园的
短信发送 / 登录 / 宿舍列表 / 余额查询接口，拿到会话后存在本机。
你不需要装 HttpCanary、不需要配代理、不需要看任何请求头。

登录后：
- 手机号、学校、宿舍位置自动写入 `data/power.db` 与 `config.yaml`
- 房间自动登记（含电价、告警阈值，默认 0.538 元/度、20 度/5 度）
- 之后 `python cli.py collect` / `loop` 直接可用

**单一学校**：`school_code` 只在首次登录时选一次，之后所有请求都固定用它，
重新登录也不会再问你。

### 模式 B：`demo`（零凭据）

演示用，随机生成带真实感的用电曲线（双峰、周末偏高、偶发大功率、自动充值、周期性异常高耗）。
分析引擎和仪表盘的所有功能都能在这上面验证。

### 模式 C：`xiaofubao`（直连上游，需要抓包）

只有你想彻底绕开第三方时才需要，代价是要自己抓 `shiroJID` 和 `ymId`：

```yaml
source:
  type: xiaofubao
  shiro_jid: "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
  ym_id: "1234567"
```

抓包步骤：手机装「易校园」+ HttpCanary（iOS 用 Stream），登录后点一次「电费查询」，
在 `application.xiaofubao.com/app/electric/queryISIMSRoomSurplus` 请求里取
Cookie 的 `shiroJID` 与参数的 `ymId`。

> 说明：上游的登录接口没有公开文档，路径是混淆的（探测下来是 catch-all，猜不出真实路径），
> 所以「不抓包」这条路走的是模式 A。模式 C 作为备选保留。

### 多房间 / 多电表终端

`nofish` 模式下绑定宿舍会自动生成房间记录。想同时盯多个房间，
可以手工往 `rooms` 数组里加条目，仪表盘左上角可切换。

## 八、分析算法说明

### 8.1 充值识别

逐对相邻读数求差 `Δ = b₁ - b₀`：

- `Δ > 3 元` → 判定为**充值**，该片段用电记 0，并写入 `events` 表
- 否则 → 用电 `max(0, -Δ)`，杜绝抖动造成的负消耗

**短时间内的多次跳升会合并成一次**（上游有时把一次充值分两条回传，比如 6.45 → 80.6 → 155.35）。

### 8.2 数据修正识别（抄表 / 换表）

宿舍用电有物理上限。若某片段反推出的功率超过 **3.5 kW**（`ADJUST_RATE_KW`），
那不可能是真实用电，而是抄表修正 / 换表 / 系统对账 —— 判为 `adjust`，**不计入用电统计**。

实测数据里确实出现过：`09-22 21:00` 余额从 107.32 直接掉到 39.06（1 小时掉 68.26 元）。
不加识别的话这天会被算成 130 度、并把 21:00 拉到全天 68% 的用电占比，整张报表就废了。

```
识别后：近 7 日均耗 13.09 度/天（原 38.47）
        高峰时段 20:00(10.08%)（原 21:00 68.13%）
数据修正：2026-09-22T21:00 跳变 68.26 元
```

### 8.3 日聚合与「可用日」筛选 ⚠️

**这一节是踩过坑之后加的，直接影响数字准不准。**

按自然日聚合后，会给每一天打三个标记：

| 标记 | 含义 |
|---|---|
| `complete` | 这一天是否**已经过完**（今天还没结束，消耗必然偏低） |
| `stale` | 这一天是否**落在数据卡住区间内**（上游没更新 ≠ 没用电器） |
| `usable` | 是否可用于计算日均 / 速率 / 预测 / 分布 / 周内画像 |

**所有统计量只使用 `usable` 的日子。**

不这么做的后果（真实踩坑）：

```
余额 152.74 元
  ✗ 错误算法：把「今天半天」+「4 个卡住日」一起平均 → 7.04 元/天 → 说能用 24.8 天
  ✓ 正确算法：只用 3 个完整用电日（09-23/24/25）      → 10.29 元/天 → 只能用 15.0 天
```

差了一倍多，而且方向是**危险的**——会让你以为还早，结果突然断电。

具体被排除的日子会在报告和仪表盘上写出来：

```
统计口径      基于 3 个完整用电日计算；已排除今天（2026-09-26，仅统计到当前，2.61）；已排除 4 个数据卡住日
              纳入的日子：2026-09-23、2026-09-24、2026-09-25
              已排除卡住日：2026-09-19、2026-09-20、2026-09-21、2026-09-22
```

受影响的分析：`avg7` / `avg14` / 耗尽预测 / 分布直方图 / 周内画像 / 异常检测。

### 8.4 异常检测（MAD）

比 3σ 更抗极端值：

```
score = 0.6745 × (x − median) / MAD
|score| ≥ 3  →  异常（正为 spike，负为 drop）
```

另有 `detect_continuous_drain()`：连续 ≥6 小时功率 ≥0.35 kW 即报"连续高耗"，专抓忘关空调。

### 8.4 耗尽预测

单纯取平均日耗会很飘。这里用**加权线性回归 + EWMA 混合**：

```
日耗预测 = 0.6 × 加权回归趋势值 + 0.4 × EWMA 平滑值
剩余天数 = 当前余额 / 日耗预测
```

- 回归权重 `w_i = 1 + i/(n−1)`，越近的日期权重越大，能跟上季节变化
- 残差标准差给出乐观/悲观区间
- **速率太小时不硬算**：若近期日均 < 0.05（宿舍长期没人、余额一直不动），
  直接返回"无法预测"，避免算出"9999 年才用完"甚至 `timedelta` 溢出崩溃
- 输出 `trend`（上升/下降/平稳），提醒你是否在用得越来越凶

### 8.5 上游历史自动回填

上游 `records/{phone}?days=7` 自带 **7 天逐小时**历史（实测 167 个点）。
本地读数不足 3 条时，采集会自动回填这批历史 —— 所以**刚登录就有曲线**，不用干等一周。

### 8.6 时段画像

把每个片段按其**起始小时**归桶，得到 24 小时的 `平均功率(kW)`、`累计度数`、`占比`。
宿舍场景下典型结果是早晚双峰（7-9 点、19-24 点）——如果你的凌晨占比异常高，说明有电器没关。

## 八点五、上游刷新时刻（实测）

**易校园在每小时第 26~28 分钟刷新余额。**

测量方法（`/tmp/probe_upstream.py`）：每 2 分钟查一次余额，连续 2 小时，记录跳变时刻。

```
16:26(150.57) → 16:28(149.97)   窗口 = 第 26~28 分钟
17:26(149.97) → 17:28(149.27)   窗口 = 第 26~28 分钟
```

两次窗口完全重合，说明是固定时刻，不是随机的。

### 为什么采集设在第 5 分

```
上游更新     每小时第 27 分
我们采集     每小时第 5 分
间距         22 分钟
```

采样点落在「上次更新后 38 分钟、下次更新前 22 分钟」，两头都留得开。

**不要改成 27 附近。** 采样时刻若和更新时间挨得太近，某次可能落在更新前、下次落在更新后，
导致一个小时的用量被算成两小时或零。

### 由此产生的一个正常现象

读数偶尔会「连着两个采集点数值完全一样」，例如：

```
15:05  151.09   ← 读到的是 14:27 的状态
15:32  150.57   ← 跨过了 15:27 的更新
16:05  150.57   ← 16:27 还没到，还是 15:27 的状态
```

这不是采集故障 —— 是两次读取落在同一个上游更新周期里。上游一小时只刷新一次，
这已经是它能给出的最高时间分辨率。

**同理，"当前小时"的功率在整点前是临时的**：例如 15:37 时第 15 小时只统计了 33 分钟，
等 16:05 采到新读数后会按整小时重算。同一笔花费，分母从 33 分钟变 60 分钟，
功率数字会明显下降 —— 这是正常的，不是算错。

## 八点六、数据保存与备份

### 数据是存起来的，不是每次读 7 天

很多人会误以为「项目只拉 7 天数据」。实际情况是：

```
上游（易校园）只保留 7 天历史
        │
        ├─ 建立项目时一次性回填 7 天 ──▶ 让你立刻有曲线看
        │
        └─ 之后每小时采集 1 条 ────────▶ 永久累积在本地 SQLite

本地 data/power.db  ══▶  唯一的长历史来源
```

回填代码的判断条件：

```python
thin = [r for r in rooms if db.count_readings(conn, r["room_key"]) < 3]
if thin:
    auto_backfill = backfill_from_nofish(cfg, days=7)
```

**只有房间读数少于 3 条时才回填。** 一旦攒够，这段逻辑永远不再触发。

### 上游到底能给多少

实测（2026-09-26）：

```
?days=3   →  72 条    (3×24=72，完整)
?days=7   → 167 条    (7×24=168，完整)
?days=14  →  15 条    ← 不升反降
?days=30  →  20 条
?days=90  →  21 条
```

**7 天是硬上限**，要更久的数据只能靠本地累积。所以：

> ⚠️ **`data/power.db` 丢了，就只剩 7 天。** 这是整个项目里唯一不可再生的东西。

### 存储占用

读数表**只增不减**，没有任何清理逻辑。按每小时 1 条算：

| 周期 | 条数 | 占用 |
|---|---|---|
| 每天 | 24 | +14.6 KB |
| 每月 | 720 | +437 KB |
| 每年 | 8760 | +5.3 MB |

一年才 5 MB，不需要清理。

每条读数还会存下上游的完整原始响应（`raw` 字段），方便日后对账：

```json
{"phone": "13800138000", "surplus_amount": 148.56,
```

## 八点七、气温数据（Open-Meteo）

### 为什么加气温

用电的大头是空调，而空调耗电由气温决定。加上气温之后：

```
现在：  日耗 = f(时间)                 ← 只能靠"最近涨了还是跌了"猜
目标：  日耗 = f(气温, 作息)           ← 天凉了自动把预估值调低
```

数据源用 [Open-Meteo](https://open-meteo.com/)：

- **免费、不需要 key、没有账号体系** —— 不引入任何凭据，也不涉及个人信息
- 一个接口同时给「过去 92 天」和「未来 16 天」的逐小时气温
- `timezone=Asia/Shanghai`，拿到的直接是本地时间

```yaml
app:
  weather:
    enabled: true
    latitude: 30.27          # 杭州
    longitude: 120.16
    timezone: Asia/Shanghai
    past_days: 14            # 每次回看多少天（上限 92）
    forecast_days: 16        # 往后取多少天（上限 16）
```

### ⚠️ 现在只存，不参与计算

**这是有意的。** 可用样本只有几天，这时候去拟合「气温系数」必然过拟合 ——
4 个点拟合出来的斜率基本是噪声，外推就会得到「150 块能用 24.8 天」那类结论。

所以当前阶段：

| 阶段 | 做什么 |
|---|---|
| **现在** | 每天拉一次气温存起来，**不参与任何计算** |
| 攒够 2~3 周 | 用历史气温 + 历史耗电，拟合「气温 → 夜间基线」的关系 |
| 拟合完成 | 用未来气温做预测，降温时自动调低预估值 |

### 为什么是「夜间基线」而不是「空调开关」

宿舍里看不到单台设备的功率，只能看到全屋总和。但空调有个干净的特征：

```
夜间最低功率 = 待机底噪（路由、充电器…） + 空调负载
                ↑ 基本恒定，~50-100W      ↑ 随气温变
```

所以不需要识别「空调开的还是关的」，只要看基线在哪：

| 情况 | 夜间基线 |
|---|---|
| 空调开着 | ~350 W |
| 空调关了（天凉了） | 会掉到 ~80 W |

**这个跳变本身就是信号**，能拟合出的形式是：

```
夜间基线(气温) = 待机底噪 + max(0, a + b × (气温 − T阈值))
                            ↑ 气温低于阈值时这部分归零 → 基线掉到底噪
```

### 命令

```bash
python cli.py weather          # 看现状
python cli.py weather fetch    # 立刻拉一次
```

```
数据源      Open-Meteo（免费，无需 key）
坐标        30.27, 120.16  Asia/Shanghai
记录条数    720 小时
覆盖范围    2026-09-13T00:00 → 2026-10-12T23:00
  已发生    348 小时（14.5 天）
  预报      372 小时（15.5 天）

```

`serve` 启动时、以及每轮采集后都会检查一次，**每天只拉一次**（预报一天更新几次足够）。

拉取失败不会影响采集 —— 只打一行日志，正常流程继续。

### 关于课表

有人会想到「把课表告诉模型，让它知道什么时候有人在」。

**现在不要这么做。** 理由：

```
可用样本   4 天
课表特征   7 天 × N 个时段 = 几十个参数
           ↑ 参数量远超样本量 → 必然记住噪声
```

课表**换个用途就很有价值**：

| 用途 | 值不值 |
|---|---|
| 当模型特征 | ✗ 现在必然过拟合 |
| 给日子打标签（上课日/周末/放假） | ✓ 一个布尔量，不算参数 |
| 验证模型学到的东西 | ✓ 「模型学出 10-12 点没人」和课表对上，是个好信号 |
| 自动填 `vacancy` 空置期 | ✓ |

**先让数据自己说话**，等攒到 2~3 个月再拿课表验证。

## 八点八、日类型（上课日 / 周末 / 假期 / 考试周）

### 为什么要分日类型

用电水平跟「今天是什么日子」强相关：

| 日类型 | 热天 | 冷天 |
|---|---|---|
| **上课日** | 下课开空调 + 打游戏，晚上概率更高 | 只开电脑 |
| **周末** | 全天可能空调 + 游戏 | 只开电脑 |
| **短假**（清明/端午/中秋） | **一定有人** → 空调 + 游戏 | 只开电脑 |
| **长假**（五一/国庆） | **可能没人** ⚠️ 需要识别；有人则 24h 空调 + 游戏 | 可能没人；有人则电脑 |
| **考试周** | **除了考试那几个小时，基本全天在宿舍** | 同上 |
| **寒暑假** | 大概率没人；有人则极端（通宵） | 同上 |

日类型(6) × 气温区间(2) = 12 种组合。每种要几个样本才能估出水平，
所以**跨季节的几个月数据是必须的**。

### ⚠️ 日历只给「假设」，结论必须由数据给

这是整个设计里最关键的一条：

```
不能因为日历写着国庆，就断定宿舍没人 ——
有人留下打游戏是完全正常的。
```

所以分工是：

| 谁 | 负责什么 |
|---|---|
| **日历** | 提供「怀疑窗口」—— 这段是长假，重点看一下 |
| **数据** | 给出**结论** —— 基线掉到 ~80W 才算没人；还在 350W 就是有人 |

`cli.py daytype` 的输出里也写了这句提醒，避免以后误用。

### 9.1 部署后还需要登录吗？

**分情况，结论是：正常情况不需要，会话过期时需要一次，而且会邮件通知你。**

| 场景 | 是否需要重新登录 |
|---|---|
| 重启服务器 / 重启进程 / 换机器（拷贝 data 目录） | **不需要**。登录态存在 `data/power.db`，进程起来直接用 |
| 上游会话自然过期（通常几周） | **需要**，重新收一次短信验证码 |
| 手机号换了 / 被上游踢下线 | 需要 |
| 用 `xiaofubao` 直连模式，`shiroJID` 过期 | 需要（重新粘一次 Cookie） |

关键机制：

- **登录态落库**：`data/power.db` 的 `meta` 表存了 phone / school_code / logged_in_at，重启不丢
- **过期自动发现**：每轮采集失败时会去问一次上游，确认是 `need_relogin`，然后
  1. 写入告警表，仪表盘右上角亮出「重新登录」按钮
  2. **发邮件通知你**（`rules.session_expired`）
- **远程重登**：把 `app.host` 改成 `0.0.0.0`，人在外面也能打开网页重新登录

所以 24 小时跑起来后，你只需要：**收到「登录已过期」的邮件时，打开网页点一下重新登录**。

> 想彻底免掉这一步，用 `xiaofubao` 直连模式粘一次 `shiroJID` 也行 —— 但它同样会过期，
> 本质上是同一件事。`nofish` 模式的好处是过期后你自己就能收短信恢复，不用抓包。

### 9.2 采集频率：对齐易校园的小时更新

易校园 **每小时**更新一次电费，所以默认配置就是小时级：

```yaml
collect:
  interval_minutes: 60      # 每小时
  minute_offset: 5          # 整点后第 5 分钟采，等上游更新完
  jitter_seconds: 90        # 附加 0~90 秒随机抖动
  retry: 3                  # 失败重试 3 次
  retry_delay_seconds: 20
```

调度是**整点对齐**的（不是"从现在起每 60 分钟"）：

```
现在 09:00 -> 下次 09:05
现在 09:04 -> 下次 09:05
现在 09:05 -> 下次 09:35   # 若 interval=30 则更密
现在 09:30 -> 下次 09:35
现在 23:58 -> 次日 00:05
```

### 9.4 Windows（任务计划程序）

```powershell
# 整点后第 5 分钟采集一次（每小时）
schtasks /create /tn "yischool-power-collect" /tr "python E:\app\yischool-power\cli.py collect" /sc hourly /mo 1 /st 00:05 /f

# 开机常驻 Web 服务
schtasks /create /tn "yischool-power-serve" /tr "python E:\app\yischool-power\cli.py serve" /sc onstart /f
```

更推荐直接跑 `python cli.py loop`（自带整点对齐），用 `nssm` 或任务计划包成服务。

## 十、邮件告警配置

### 10.1 发邮件需要一个发件账号

邮件不是凭空发出去的，链路上必须有**一个发件邮箱**：

```
你的服务器  ──用你的邮箱账号+授权码登录──▶  QQ邮箱的 SMTP 服务器  ──▶  收件人
```

不需要自己搭邮件服务器，但需要一个**已有的邮箱**（QQ 邮箱最方便，学校邮箱也行）。

```yaml
alerts:
  enabled: true
  email:
    enabled: true
    smtp_host: smtp.qq.com
    smtp_port: 465
    use_ssl: true
    username: "you@qq.com"
    password: "16位授权码"            # ← 不是QQ密码，是单独生成的
    from_addr: ""                     # 留空=用 username
    to_addrs:
      - "you@qq.com"
      - "roommate@qq.com"             # 可以发给室友
    subject_prefix: "[寝室电费]"
```

**授权码怎么拿：**

| 邮箱 | 步骤 |
|---|---|
| QQ | 设置 → 账户 → 「POP3/IMAP/SMTP服务」开启 → 生成**授权码**（16 位） |
| 163 | 设置 → POP3/SMTP/IMAP → 开启 SMTP → 获取**授权码** |
| Gmail | 需先开启两步验证 → 应用专用密码 |
| 学校邮箱 | 问信息中心要 SMTP 地址，通常 587 + STARTTLS |

验证配置：

```bash
python cli.py test-email
# ✓ 已发送至 you@qq.com
```

### 10.1b 不想用邮箱？用 Webhook

其实**根本不需要邮箱账号**也能收到提醒：

| 方式 | 需要什么 | 适合 |
|---|---|---|
| **Bark** | App Store 装 Bark，得到一个 URL | iPhone，最快 |
| **企业微信机器人** | 群里加机器人，复制 Webhook URL | 发到宿舍群 |
| **钉钉机器人** | 同上 | 同上 |
| **Server酱** | 微信扫码绑定 | 安卓 |

填 `alerts.webhook_url` 即可，和邮件可以同时用，也可以只用这个：

```yaml
alerts:
  webhook_url: "https://api.day.app/你的BarkKey"
```

不想收任何提醒就把 `alerts.enabled` 设为 `false`，其余功能不受影响。

### 10.2 会收到哪些告警

| 告警 | 触发条件 | 级别 |
|---|---|---|
| **电费告急** | 余额 ≤ `critical_kwh` | 🔴 严重 |
| **电费偏低** | 余额 ≤ `warn_kwh` | 🟠 提醒 |
| **即将耗尽预警** | 按当前速率 `forecast_days` 天内用完 | 🟠 提醒 |
| **用电量异常偏高** | 某天消耗偏离中位数 ≥3σ（MAD） | 🟠 提醒 |
| **数据卡住** | 余额连续 `stale_hours` 小时一分钱没动 | 🟠 / 超 72h 升为 🔴 |
| **连续高耗** | 连续 ≥6 小时功率 ≥0.35 kW（忘关空调） | 🔵 提示 |
| **登录已过期** | 上游返回 `need_relogin` | 🔴 严重 |
| **连续采集失败** | 连续失败 ≥ `collect_failed_times` 次 | 🟠 提醒 |

邮件长这样：

```
主题：[寝室电费] 3号楼 502 电费偏低

房间：3号楼 502
当前余额：15.20 元
日均消耗：6.16 元/天
预计耗尽：2026-10-03（还有 2.5 天）
告警线：20 元

建议提前充值。
```

### 10.3 防止刷屏

所有告警都过 `dedupe_hours`（默认 12 小时）静默期 —— 同一类告警 12 小时内只发一封。
余额一直在低位也不会每轮采集都发。

### 10.4 先预演，别等出事才发现配错

```bash
python cli.py test-alert     # 跑一遍规则，看会报什么，不推送不落库
```

输出示例：

```
  [warn] 3号楼 502 电费数据卡住 82 小时
        房间：3号楼 502
        卡住起始：2026-09-19 11:00
        已持续：82.0 小时
        保持不变的值：107.32 元
```

## 十一、常见问题

**Q：`check` 报「尚未登录」？**
A：运行 `python cli.py login`，或打开 http://127.0.0.1:8787/login 用手机验证码登录。不需要抓包。

**Q：会话过期了怎么办？**
A：会发邮件通知你。打开仪表盘点右上角「重新登录」→ 收一次验证码 → 完成。
不用重选学校，也不用重选宿舍。

**Q：服务器上跑着，重启要不要重新登录？**
A：不用。登录态在 `data/power.db` 里，只要这个文件不丢，重启进程/重启机器都直接用。
只有上游会话真正过期时才需要重新验证一次。

**Q：验证码收不到 / 到得很慢？**
A：**易校园的短信实测可能延迟 10~20 分钟才到**，这是上游短信网关的延迟，不是发送失败。

先点登录页上的 **「运行自检」**，它会逐项告诉你卡在哪一步：

```
✓ 数据源类型：nofish
✓ 上游连通性：学校列表接口正常，返回 50 所学校
✓ 网络路径：经代理 / 直连
✓ 手机号：138****0000
✓ 账号记录：上游暂无该号码记录（不影响发码）
✓ 发码冷却：可以发送
✓ 本次发码：已于 09:31:20 发送，已等待 12 分 04 秒，累计发送 2 次
```

要点：

1. **耐心等 10~20 分钟**，页面显示「已等待 xx 分 xx 秒」，刷新页面也不会丢。
2. **重复获取发的是同一条验证码，不会覆盖** —— 所以收不到时可以放心重发，
   不需要担心作废。上游只限制 60 秒一次（本项目已加本地 60 秒冷却）。
3. 若等待超过 30 分钟仍未到，改用下面的「粘贴易校园会话」方式绕过短信。
4. 上游偶发 HTTP 500（`服务器错误`）时，页面上会**如实显示上游原话**，不会假装成功。

> 实现说明：上游失败时**可能仍返回 HTTP 200**。成功信封是 `{"status":"ok","message":"验证码已发送"}`，
> 失败信封是 `{"code":500,"msg":"Server error"}` 或 `{"detail":"短信发送超限，请一分钟后再试"}`。
> 本项目会校验响应体（`AuthClient._unwrap`）并把上游原话透到页面上，
> 所以不会再出现「页面显示已发送、实际没发」的情况。

**Q：不想等短信，有别的登录办法吗？**
A：有。登录页底部有 **「粘贴易校园会话」**，**不需要抓包工具**：

1. 电脑浏览器打开 <https://application.xiaofubao.com/>（易校园网页版）
2. 正常登录（微信扫码，就是你平时登录易校园的方式）
3. 按 **F12** → **Application** → **Cookies** → 找到 `shiroJID`，复制它的值
4. 粘贴到登录页的输入框 → 点「导入会话」

程序会自动用这个 Cookie 探出 `ymId` 和房间信息并登记好，不用你去请求里翻参数。

> 说明：`shiroJID` **本身就是登录成功后服务器下发的会话票据**（一个 Cookie）。
> 所以这不是「绕过登录」，只是把登录动作换到易校园自己的网页上做，
> 再把结果票据交给本程序使用。抓包工具只是取这个 Cookie 的一种手段，
> 用浏览器 F12 复制更简单。

**Q：为什么不用抓包也能登录？**
A：登录流程由本项目的后端 `ysp/auth.py` 代你完成——发码、校验、取宿舍列表、取余额都在服务端走，
你只在浏览器里输验证码。所以不需要装抓包工具，也不需要配代理。

**Q：采集报「无法从响应中解析余额」？**
A：上游字段名变了。`ysp/adapters/base.py` 里的 `_KWH_KEYS` / `_CNY_KEYS` 加一个候选字段名即可；原始响应已存在 `readings.raw` 列，可直接查看。

**Q：仪表盘显示"没有可用房间"？**
A：先 `python cli.py init`，再 `python cli.py seed-demo`。

**Q：数据存在哪？**
A：`data/power.db`（SQLite）。直接用 DB Browser for SQLite 打开就能看，或走 `/api/export.csv` 导出。

**Q：会不会被学校发现高频请求？**
A：默认 30 分钟一次，且采集时每房间随机 sleep 0.4~1.2 秒。想更保守就把 `collect.interval_minutes` 调到 60。别改到 1 分钟。

**Q：能同时盯多个寝室吗？**
A：`config.yaml` 的 `rooms` 写多条，仪表盘左上角切换。
